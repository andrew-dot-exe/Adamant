# Введение
В качестве формата сохранения данных был выбран **Markdown**-файл - его преимущество заключается в простом синтаксисе, который легко парсить и можно писать форматированные тексты буквально везде (к примеру, сейчас этот текст пишется в текстовом редакторе ```nvim```. К тому же, данный формат очень хорошо масштабируется, прекрасным примером могут быть README-файлы на GitHub или md-файлы в Obsidian. 
В данном проекте этот формат будет использоваться для хранения лекций.
## Парсинг Markdown
Базовое правило MD - отсутствие пробелов между текстом и "тегами", пример:
- **правильно**
- ** неправильно **.

Сам парсинг очень простой, для начала надо выделить основные единицы форматирования текста, а именно:
- полужирный текст (** это две звездочки перед и после блока полужирного текста, но без пробелов после и перед звездочками **)
- подчекрнутый текст (у MD нет определенного синтаксиса для подчеркнутого текста, так что пусть будет, например блок !* !*, работает как и полужирный текст)
- выделение цветом (поддерживается не всеми, надо думать о своем, к примеру, ==текст==, можно добавить определение цвета, например, =r текст на красном фоне  r= или, на русском, =к текст на красном фоне =). Думаю, суть ясна. 
- блоки кода (тройной знак ударения, как и везде)
- таблицы, но не совсем понятно, как их "русифицировать" и представить в выводе

## Техническая сторона парсинга
- Класс парсера должен поддерживать работу как с файловым потоком, так и со строкой. Строка должна быть разбита на подстроки при помощи \n, если она должна быть представлена как многостройчный текст. Заголовки обязательно должны быть представлены как единичная строка с соотвествующим уровню количеству решеток с переходоми на новую строку. Пример:

```java
    String textWithHeading = "# First level heading\nSome text here.";
```

- Парсер должен поддерживать строки с форматом UTF-8, планируется поддержка эмодзи в виде UTF-8 codes.
- Парсер должен быть полностью покрыт тестами, в том числе, при добавлении новых функций.
- Парсер не должен быть зависим от внешних библиотек и от конкретных реализации. Необходимо использовать абстракции и интерфейсы, если это потребуется.
Список требований будет пополняться.

### Input
Строка или файловый поток. При вводе из файлового потока использовать кэширование.
### Output
Класс ```MarkdownText```, в котором будет храниться текст, очищенный от распознанных символов, а также списки из классов Range, которые хранят диапазоны текста, форматированные тем или иным образом.
#### Класс ```Range```
Класс, который имеет два поля: поле начала диапазона и поле конца диапазона, соответственно, представляя диапазон.

### Взаимодействие с фронтенд-частью
В данном случае фронтендом может быть что угодно: текстовое поле, HTML, PDF. Взаимодействие парсера с фронтендом будет происходить при помощи интерфейса, который декларирует обязательные методы для фронтенда.
